4.6 Glossary¶

The terms mConfig uses, in the order an application developer meets them: first what you read and write, then how mConfig finds it, then the parts that extend mConfig. Each term has one meaning in this documentation and in the API; where everyday English or another library uses the same word differently, the last column says so.

Terms marked planned describe the design of an upcoming release; the API for them does not exist yet.

Reading configuration¶

Term Meaning Example Not to be confused with
Configuration A named set of entries an application reads, assembled from layers in scope order. factory.getConfig("network") mConfig settings (features)
Entry / key One value with its metadata. The key is hierarchical, with / as separator; a dot is part of the key. server/port –
Scope One of the 10 priority tiers, from POLICY (highest) to PRODUCT (lowest). See Scopes. HOST, USER –
Schema Declares a configuration's keys: type, default, validation, SECRET. See Configuration Schemas. network.mconfig-schema.json –
Event A record of something noteworthy during the factory's life, kept in the factory's event list. See Config Events. SOURCE_UNAVAILABLE log lines

Where configuration comes from¶

Term Meaning Example Not to be confused with
Storage A kind of place where configuration is kept. Technical term; the documentation also says source informally, as in addSource() and the module names mConfigSource…. Each storage has a storage ID; the features STORAGE_TYPE_PRIORITIES and STORAGE_TYPE_ALLOW_ALL_STORAGES take lists of storage IDs. files, JAR resources, environment variables, Windows registry, Vault, ZooKeeper location (a place within a storage)
Format How stored data is written. properties, YAML, JSON, TOML storage
Location A specific place within a storage, with a scope. A search location may yield several layer locations. Locations stay traceable for every entry, secret ones included. /etc/opt/acme/shop/ (HOST), one file in it storage
Search list The ordered list of search locations a factory reads. mconfig <company>:<app> search-paths –
Layer The entries read from one layer location. the contents of one network.yaml –
Storage provider (planned, 0.9.0) The plug-in for one kind of storage: it decides whether the storage may run, proposes default instances, and creates instances. "Provider" in the sense of a Terraform or OAuth provider. Today one storage object does both jobs, provider and instance. the Vault provider a ServiceLoader "service provider" (Java's term for any implementation found through META-INF/services)
Storage instance (planned, 0.9.0) One configured use of a storage, created by its provider. Vault at https://vault.example.com:8200 storage (the kind)
Secrets provider A provider whose instances supply secret values. – the SECRET schema property (marks an entry; see Secrets Concept)

Setting up mConfig itself¶

Term Meaning Example Not to be confused with
Feature (mConfig setting) A setting that controls mConfig itself, not the application. Set in code, through runtime settings, or in the component file; each has a setting level that limits where it may be set. See Config Features. TEST_MODE, VAULT_BYPASS_TEST application configuration; "feature" in the sense of functionality
Component A program or library that uses mConfig under its own company and application name. Its component file .config/<company>/<app>/mconfig.properties sets features for its own factories only. an application, or a library inside it that builds its own factory factory hook
Bootstrap configuration An ordinary configuration of the application that a module reads to set itself up, through the usual layers. vault.properties with the Vault address features
Fact (planned, 0.9.2) Something mConfig knows about the environment it runs in: host name, user, operating system; in clouds also role, zone, region, tenant. Detected by mConfig, published by modules, or set explicitly; read-only once final. Used to find HOST to ORGANIZATION locations in shared storages. host = web-3.example.com, zone = eu-central-1a feature

Rule of thumb: a feature says how mConfig should behave (you set it); a fact says where mConfig is (it finds out).

Extending mConfig¶

Term Meaning Example Not to be confused with
Module A JAR that plugs into mConfig. Since 0.9.0 it announces itself through ConfigModuleInterface. mConfigSourceVault, mConfigFormatYAMLwithJackson a Java module (JPMS); a module JAR may or may not be a JPMS module
Module descriptor (since 0.9.0) The data a module returns about itself, without side effects: ID, capabilities, features, contributions; later also fact keys and bootstrap reads. ConfigModuleDescriptor –
Contribution One thing a module adds to a factory. a storage, a format, a logger, a factory hook, a schema provider, a secrets provider –
Factory hook A contribution that takes part in the factory's life cycle (initialise, post-initialise, close). Implemented today through the interface ConfigFactoryComponent, which will be renamed at a later interface change. the secrets adapter in mConfigSecrets, the schema exporter in mConfigSourceFilesystem component
Capability (since 0.9.0) A job that exactly one module may do at a time, with an ID and a feature-name prefix. Implementations of the same job share the capability and exclude each other: if two are present, both are refused with a WARNING that names the fix (DISABLED_MODULE_IDS). kubernetes (prefix KUBERNETES_; implemented with the JDK HTTP client or with Fabric8), windows-registry (jnr-ffi or JNI) feature (a capability owns feature names); the fact role
Bring-up (planned, 0.9.3) Starting the storage instances in dependency order. Each step brings one instance to READY or UNAVAILABLE. A bootstrap read sees only the scopes it asks for, and only instances that are READY. The order is the bootstrap graph. file → OS credential store → Vault → AWS init() / postInit() of the 0.8 storages
Context The object mConfig hands to a module during set-up: BootstrapConfigContext for storages, ConfigFactoryInstanceContext for factory hooks. ctx.getRestrictedConfig("vault", scopes) facts

Words used loosely¶

  • source: informal for storage, or for one of its locations; used in addSource() and module names.
  • provider: in mConfig, the plug-in for one kind of external system (storage provider, secrets provider). The schema provider (ConfigSchemaProvider) is a looser use: it supplies schemas, not connections. Java's ServiceLoader calls every implementation found through META-INF/services a "service provider"; that is not an mConfig term.
